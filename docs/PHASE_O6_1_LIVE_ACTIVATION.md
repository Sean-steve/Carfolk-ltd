# Carfolk — O6.1 Production Error Handling Activation & Monitoring

## State and release gates

This phase adds an **authenticated web-PHP upload diagnostics page** (`/manage/system-health`) and a **GitHub Actions public uptime workflow**. GitHub cannot change HostPinnacle PHP limits, validate authenticated photo POSTs, or activate the existing cPanel Cron deployer. Mark production deployment **not certified** until the owner completes and records the checks below.

## 1. HostPinnacle operational change — before release

1. Confirm a restorable backup of the PostgreSQL database and all existing vehicle photos. Keep secrets and dumps out of `public_html` and GitHub.
2. In cPanel **MultiPHP Manager** confirm `carfolkltd.com` runs PHP 8.4.
3. In cPanel **MultiPHP INI Editor**, select `carfolkltd.com` (or its effective PHP configuration); recommended values:
   - `upload_max_filesize=10M`
   - `post_max_size=50M`
   - `memory_limit=256M`
   - `max_file_uploads=20`
   - `max_execution_time=120`
   - `max_input_time=120`
4. Visit `https://carfolkltd.com/manage/system-health` **after code deployment** as an authenticated active admin. Confirm it reports a PHP file limit at least 8 MB, POST limit at least 41 MB and writable photo/log storage. HTTP 413 can still be generated by Apache, proxy or ModSecurity *before Laravel*; consult host support if it persists.

## 3. Authenticated live upload certification

Log in to Carfolk administration with a real operator account. Choose an existing *authorized* vehicle, then:

| Case | Expected |
| --- | --- |
| Single 1 MB JPEG | Upload succeeds; image appears on that listing and public image URL works |
| Five 6 MB JPEGs in one batch | Upload succeeds (under configured 50 MB POST) |
| Six selected photos | Client rejects before POST |
| Any photo over 8 MB | Client rejects before POST |
| More than 20 total photos | Client/server reject without partial files |
| Combined upload exceeds actual POST capacity | Client rejects before POST where browser has reliable limits |
| One file upload fails in a batch | Database/files roll back; no orphaned or duplicate photos |
| iPhone Safari (same positive + negative cases) | Same behavior; no raw HTTP 413 page for client-validated cases |
| Unauthenticated photo upload | Redirect/login or 401; must not mutate database |

Use test photos owned/approved by Carfolk and remove only specifically identified test photos after verification. **Do not automatically delete live inventory or customer records.** If a small upload still gives 413, ask HostPinnacle about Apache/ModSecurity/proxy request limits and log a host ticket. If PHP didn't receive the POST, no Laravel error page or request-ID will be available.

## 4. Monitor/alert setup

Workflow: `.github/workflows/carfolk-live-monitor.yml` (scheduled every 15 minutes + manual dispatch). It performs public read-only checks and creates **one open GitHub Issue** for a sustained public endpoint failure. On recovery it comments and closes the issue. No credentials, request bodies, lead data or logs are sent to public Issues.

Activation requirements:
- Workflow merged into **default branch main** (schedules only run there).
- GitHub Actions enabled and Issues enabled on `Sean-steve/Carfolk-ltd`.
- GitHub Actions `GITHUB_TOKEN` permitted to create issues (`issues: write` permission is specified in workflow).
- Operator subscribes to repository issue notifications; automated Issues alone **do not guarantee phone/email paging**.
- Manually dispatch one run and verify its result. Then observe scheduled runs for at least one full interval. Validate alert and recovery in a controlled **non-production test or separately approved test environment**, not by deliberately taking down the live site.

This monitor covers HTTP 200 on `/`, `/up`, `/api/v1/site`, and `/manage/login`. It does **not** detect authenticated 413 uploads, stale assets, financial/domain errors, latency SLOs, or individual failed enquiries. Server 413/error-rate monitoring must be configured in HostPinnacle logs or an approved observability provider before O6.1 can be called fully complete.
